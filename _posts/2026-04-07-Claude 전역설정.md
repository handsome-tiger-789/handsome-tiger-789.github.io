```md
# Global Development Guidelines

## Mandatory Pre-Edit Procedure

Before modifying any code, always present an execution plan in the format below
and wait for explicit user approval before proceeding.

### Plan Format
1. **Purpose**: What and why
2. **Files to change**: List of file paths
3. **Change summary**: What changes in each file
4. **Impact**: Potential side effects
5. **Rollback**: How to revert if something goes wrong

Never run Edit, Write, or file creation without prior approval.

## Tech Stack
- Backend: Java / Spring Boot
  - Java version: check `.java-version` or `pom.xml <java.version>`
  - Spring Boot version: check `pom.xml <parent>` block
- Frontend: Node.js / React
  - Node version: check `.nvmrc` or `package.json engines` field
  - Package versions: always read `package.json` before suggesting changes
- Build tools: Maven / Gradle
- Dependencies: Always use exact versions from pom.xml/package.json

## Coding Conventions

### Comments (Required)
- Add JSDoc/JavaDoc to all public methods/classes
- Inline comments for complex logic (10+ lines)
- Include version + reason when adding dependencies

### Exception Handling
- Use unchecked exceptions for programming errors
- Define custom exception hierarchy under a base `ApplicationException`
- Never swallow exceptions silently; always log with sufficient context

### Logging (SLF4J)
- ERROR: system failures requiring immediate attention
- WARN: recoverable issues or unexpected but non-fatal states
- INFO: business-significant events only (not chatty)
- DEBUG: development/troubleshooting only, never in hot paths
- Use MDC for request tracing (requestId, userId at minimum)

### Testing
- Unit tests: service layer and below; mock external dependencies
- Integration tests: repository layer; use `@SpringBootTest` sparingly
- Target 80%+ coverage on service layer
- Test method naming: `methodName_scenario_expectedResult`

### API Design
- REST response envelope: `{ data, error, meta }`
- Error codes: domain-prefixed (e.g. `USER_NOT_FOUND`, `ORDER_INVALID_STATE`)
- Validate all inputs at controller boundary using `@Valid` + custom validators
- Never expose internal stack traces in API responses

### Dependency Management
- Specify exact versions in pom.xml/package.json
- Never use "latest"
- Include change reason + test results in Plan

## Git / Deployment
- Do NOT run git commit, push, checkout, add, or stash. User handles all git operations.
  - `git stash` is also blocked: stash operations can silently discard in-progress work.
- Do NOT run Docker commands. User handles all deployment operations.

## Response Style
- Be concise. Avoid redundant explanations.
- Do not list multiple alternatives unless explicitly asked.
- Always include relevant comments with version information.
```

```md
 # Global Development Guidelines

 ## Mandatory Pre-Edit Procedure

 Before modifying any code, always present an execution plan in the format below
 and wait for explicit user approval before proceeding.

 ### Plan Format
 1. **Purpose**: What and why
 2. **Files to change**: List of file paths
 3. **Change summary**: What changes in each file
 4. **Impact**: Potential side effects
 5. **Rollback**: How to revert if something goes wrong

 Never run Edit, Write, or file creation without prior approval.

 ## Tech Stack
 - Backend (primary): Java 17+ / Spring Boot 4.x
   - Java version: check `.java-version` or `pom.xml <java.version>`
   - Spring Boot version: check `pom.xml <parent>` block
 - Database (primary): MySQL
 - Frontend (occasional): Node.js / React
   - Node version: check `.nvmrc` or `package.json engines` field
   - Detailed frontend conventions belong in project-level CLAUDE.md
 - Build tools: Maven / Gradle
 - Dependencies: always read pom.xml/package.json before suggesting changes

 ## Coding Conventions

 ### Comments
 - JavaDoc/JSDoc only for public APIs (signatures imported by other modules)
 - Otherwise, write a comment only when the WHY is non-obvious
 - Do not write WHAT comments (well-named identifiers cover that)
 - Include version + reason when adding dependencies

 ### Exception Handling
 - Use unchecked exceptions for programming errors
 - Define custom exception hierarchy under a base `ApplicationException`
 - Never swallow exceptions silently; always log with sufficient context

 ### Logging (SLF4J)
 - ERROR: system failures requiring immediate attention
 - WARN: recoverable issues or unexpected but non-fatal states
 - INFO: business-significant events only (not chatty)
 - DEBUG: development/troubleshooting only, never in hot paths
 - Use MDC for request tracing (at minimum: traceId, requestId, userId)

 ### Testing
 - Unit tests: service layer and below; mock external dependencies
 - Integration tests: repository layer; use `@SpringBootTest` sparingly
 - Coverage: prioritize core business logic (service/domain). Follow project standard if defined; do not enforce a global
 percentage.
 - MySQL integration tests: use Testcontainers MySQL, not H2 (dialect drift causes prod surprises)
 - Test method naming: `methodName_scenario_expectedResult`

 ### API Design
 - REST response envelope: `{ data, error, meta }`
 - Error codes: domain-prefixed (e.g. `USER_NOT_FOUND`, `ORDER_INVALID_STATE`)
 - Validate all inputs at controller boundary using `@Valid` + custom validators
 - Never expose internal stack traces in API responses

 ### Dependency Management
 - Specify exact versions in pom.xml/package.json
 - Never use "latest"
 - Spring Boot starters: rely on the BOM-managed version; pin explicit version only for libraries not in the BOM
 - Include change reason + test results in Plan

 ## MySQL Operations
 - Migrations always in dedicated files (Flyway/Liquibase). No inline DDL in application code.
 - `DELETE` / `UPDATE` must include `WHERE`. Warn loudly if a query lacks one.
 - Assume `utf8mb4` charset. Report `latin1` or other non-utf8 collations immediately.
 - Index changes and `ALTER` on large tables are treated as non-trivial changes (Pre-Edit Procedure applies).

 ## Git / Deployment
 - git / docker / deploy commands are blocked via settings.json `deny`. The user handles these directly.
 - Do not attempt blocked commands; report results to the user and let them run the command.

 ## Response Style
 - Be concise. Avoid redundant explanations.
 - Do not list multiple alternatives unless explicitly asked.
```
